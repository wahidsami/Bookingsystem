## Executive Summary

Phase 1 established an isolated, safe clone of the Tenant-v2 Services workspace at `Tenant-v2/src/components/Services2Workspace.tsx` without disturbing the active production workspace (`ServicesWorkspace.tsx`), `PackagesWorkspace.tsx`, or appointment scheduling components.

Phase 2 constitutes a comprehensive forensic investigation across the entire codebase (`Tenant-v2`, `server`, `RifahMobile`, `RifahStaff`, database schemas, and migration history). The primary architectural objective of "Services 2" is to transition from the current fragmented model—where Services and Packages live in disconnected silos and Categories are globally owned by Super Admin—into a **unified, tenant-empowered catalog model** where:
1. Tenants own and curate their service categories.
2. Both standalone Services and bundled multi-service offerings ("Bundles") reside under those categories.
3. The appointment drawer and booking engine seamlessly consume this unified catalog.

### Key Forensic Findings

1. **Category Ownership is 100% Super Admin / Global Today:**
   The `service_categories` table (`rifah_clean_schema_utf8.sql:3324-3334`, `server/src/models/ServiceCategory.js`) has **no `tenantId` column**. All categories are system-wide. A hardcoded set of 21 default categories is seeded on every backend boot (`server/src/utils/seedServiceCategories.js:1-74`, invoked by `server/src/index.js:793-794`).
2. **Tenant Category Mutability is NOT IMPLEMENTED:**
   Tenants currently have read-only access via `GET /api/v1/tenant/services/categories` (`tenantServiceController.js:304-324`). There are no tenant endpoints to create, edit, delete, reorder, or archive categories. All mutation endpoints (`POST`, `PUT`, `DELETE`, `/reorder`) require Super Admin authentication and `settings:edit` permissions (`server/src/routes/adminRoutes.js:113-117`).
3. **The Service → Category Link is a Loose String Literal, Not an FK:**
   In `server/src/models/Service.js:91-95`, `category` is a `DataTypes.STRING` column (defaulting to `'general'`). There is **no database foreign key constraint** and **no Sequelize association** between `Service` and `ServiceCategory`. In the frontend, `ServicesWorkspace.tsx:231-236` defines hardcoded fallback categories (`massage-therapy`, `skincare`, `hair-care`, `nail-care`) when the API returns an empty list.
4. **Packages Have Zero Category Association Today:**
   `ServicePackage` (`server/src/models/ServicePackage.js`) contains fields for `tenantId`, `name_en`, `name_ar`, `image`, `isActive`, `totalDuration`, and `totalPrice`. It contains **no `category` or `categoryId` field**. Consequently, packages cannot be categorized or filtered by category in the current UI or appointment drawers.
5. **Packages Can Safely Become Bundles at the Persistence Layer:**
   The existing `service_packages` and `service_package_items` tables already provide 90% of the required bundle capabilities: tenant isolation, sequence ordering (`sequenceOrder`), staff pre-assignment (`defaultStaffId`), variant targeting (`variantId`), and atomic multi-step appointment generation (`server/src/services/bookingService.js:723-818`). Renaming the underlying database table is unnecessary, high-risk, and undesirable; adopting an adapter/aliasing pattern in Services 2 allows "Bundles" to be presented in the UI while retaining `ServicePackage` at the database layer.
6. **Appointment Drawer Derives Categories Client-Side:**
   In `Tenant-v2/src/components/InteractiveDrawers.tsx:699-709`, category tabs are **not fetched from any category API**. Instead, categories are dynamically generated by inspecting whatever services are in `canonicalServices` using `groupServicesByCategory` (`Tenant-v2/src/lib/serviceContract.ts:489-511`). Because packages lack a category property, `AppointmentServicesStep.tsx:175-196` renders a top-level tab split between "Services" and "Packages".

## Current Service Variant Architecture

### Storage & Model Representation
- Variants are **NOT stored in a separate table**.
- Stored as a **`JSONB` array column** on the `services` table (`Service.js:138-143`, added via migration `20260421113000-add-service-price-type-and-variants.js`).
- Each object in the `variants` JSONB array follows this schema:
  ```json
  {
    "id": "var_1713700000000",
    "name_en": "Short Hair",
    "name_ar": "شعر قصير",
    "description_en": "Up to shoulder length",
    "description_ar": "حتى مستوى الكتف",
    "duration": 45,
    "rawPrice": 100.00,
    "finalPrice": 115.00,
    "isActive": true
  }
  ```

### Variant Booking & Scheduling Behavior
- **Appointment Capture:** When an appointment is booked with a variant, `server/migrations/20260421140000-add-appointment-service-variant-snapshot.js` captures a frozen snapshot on the `Appointment` record:
  - `serviceVariantId`: String ID of the variant.
  - `serviceVariantName`: Name snapshot.
  - `serviceVariantDescription`: Description snapshot.
  - `serviceVariantDuration`: Duration snapshot.
- **Price & Duration Override:** If a variant is selected, its `finalPrice` and `duration` completely override the parent service's base `finalPrice` and `duration` (`InteractiveDrawers.tsx:1603-1604`, `AppointmentWorkspace.tsx:3447`).
- **Staff Eligibility:** Variants inherit the parent service's staff associations (`ServiceEmployee`). There is no variant-specific staff assignment.

### Can a Bundle Reference Base Service vs Variant?
- **Evidence:** `server/src/models/ServicePackageItem.js:33-36` defines:
  ```javascript
  variantId: {
      type: DataTypes.STRING,
      allowNull: true
  }
  ```
- **Conclusion:** A Bundle item **can reference either**.
  - If `variantId` is `null`: the bundle item executes as the base service.
  - If `variantId` is provided: `InteractiveDrawers.tsx:1599-1601` finds the specific variant from `service.variants`, adopting that variant's duration, name, and pricing during staging.

## Current Package Architecture

### A. Package Entity (`ServicePackage`)
- **Table:** `service_packages` (`20260905120000-create-service-packages.js:14-53`)
- **Fields:**
  - `id`: UUID PK.
  - `tenantId`: UUID FK to `tenants(id)`.
  - `name_en`: VARCHAR(150), required.
  - `name_ar`: VARCHAR(150), required.
  - `image`: VARCHAR(255), nullable thumbnail URL.
  - `isActive`: BOOLEAN, default `true`.
  - `totalDuration`: INTEGER, default 0 (derived sum of member services).
  - `totalPrice`: NUMERIC(10,2), default 0 (derived sum of member prices).
  - `createdAt`, `updatedAt`: Timestamps.

### B. Package Items (`ServicePackageItem`)
- **Table:** `service_package_items` (`20260905120000-create-service-packages.js:56-105`)
- **Fields:**
  - `id`: UUID PK.
  - `packageId`: UUID FK to `service_packages(id)` with `onDelete: 'CASCADE'`.
  - `serviceId`: UUID FK to `services(id)` with `onDelete: 'RESTRICT'` (or default).
  - `variantId`: VARCHAR(255), nullable string referencing a variant ID inside `services.variants`.
  - `defaultStaffId`: UUID FK to `staff(id)` with `onDelete: 'SET NULL'`.
  - `sequenceOrder`: INTEGER, default 0. Controls chronological execution order.

### C. Existing Package CRUD Operations
Audited from `server/src/controllers/tenantPackageController.js`:
- **Create Package:** `POST /api/v1/tenant/packages` (`lines 111-209`). Accepts `name_en`, `name_ar`, `items` (JSON array), optional image file upload.
- **Read Packages:** `GET /api/v1/tenant/packages` (`lines 15-68`). Lists packages with constituent items and nested services.
- **Read Single Package:** `GET /api/v1/tenant/packages/:id` (`lines 70-109`).
- **Update Package:** `PUT /api/v1/tenant/packages/:id` (`lines 211-309`). Updates metadata and completely replaces items transactionally.
- **Delete Package:** `DELETE /api/v1/tenant/packages/:id` (`lines 311-344`). Hard deletes the package and cascades deletion to `service_package_items`.
- **Capabilities that DO NOT Exist:**
  - Deactivate / Archive dedicated endpoints (only editing `isActive` via `PUT`).
  - Restore (no soft delete).
  - Duplicate package (not implemented).
  - Bulk actions (not implemented).

### D. Total Price and Duration Calculation
- In `tenantPackageController.js:154-159`:
  ```javascript
  const totalPrice = items.reduce((sum, item) => sum + (parseFloat(item.price) || 0), 0);
  const totalDuration = items.reduce((sum, item) => sum + (parseInt(item.duration, 10) || 0), 0);
  ```
- **Pricing Limitation:** The total price is **strictly derived as the mathematical sum** of member services. Tenants **cannot set a package discount price** (e.g., two 100 SAR services bundled for 170 SAR) in the backend.

### E. Source Service Mutation & Deletion Behavior
1. **Price/Duration Change on Source Service:**
   Existing packages store `totalPrice` and `totalDuration` as static snapshots on `service_packages`. If a base service changes price, the package record is **not automatically recalculated** until the package is updated via `PUT`.
2. **Deactivation of Source Service:**
   The package remains active. However, when loaded in the appointment drawer (`InteractiveDrawers.tsx:1597`), `canonicalServices.find(s => s.id === item.serviceId)` will omit inactive services if filtered, causing that package item to be dropped.
3. **Hard Deletion of Source Service:**
   PostgreSQL will throw a Foreign Key constraint violation error (`23503: foreign_key_violation`) if someone attempts to delete a service that is referenced by any row in `service_package_items`, because `serviceId` lacks `onDelete: 'CASCADE'`.

### F. Booking Behavior & Persistence
- Audited from `server/src/services/bookingService.js:723-818`:
  When a package is booked, the backend **does not create a single monolithic appointment**. Instead:
  1. A shared `BookingSession` record is created.
  2. For each package item in sequence, a **distinct `Appointment` record** is created.
  3. Each appointment is tagged with:
     - `packageId`: The package UUID.
     - `packageItemId`: The specific package item UUID.
     - `packageSequenceOrder`: Sequence integer (0, 1, 2...).
     - `packageSnapshot`: JSON snapshot of the package header.
     - `packageItemSnapshot`: JSON snapshot of the package item details.
     - `bookingSessionId`: Links all member appointments together.
  4. On the scheduler board (`SchedulerGrid.tsx`), each appointment renders under its assigned specialist at its sequential time, badged with a package icon.

| :--- | :--- | :--- | :--- | :--- |

| **Multi-Service Ordering**| Controlled via `sequenceOrder INT` | Step-by-step ordered execution | **100% Compatible** | None |
| **Staff Pre-assignment**| `defaultStaffId` per package item | Specialist assigned per bundle step | **100% Compatible** | None |

| **Appointment Generation**| Atomized appointments in `BookingSession`| Atomized appointments in `BookingSession`| **100% Compatible** | None |

### Semantic vs Structural Assessment
- **Can the database remain `service_packages` while UI calls it "Bundle"?**  
  **YES.** In software engineering, aliasing a database table (`ServicePackage` -> `BundleDTO`) via an API adapter layer is a standard, risk-free pattern.
- **Does anything depend on the word "package"?**  
  Yes. Invoicing (`20260906000000-add-package-to-invoice-item-type.js`), appointment fields (`packageId`, `packageItemId`, `packageSnapshot`), and entitlements (`hasServicePackages`). Renaming the database tables would break all existing migrations and require massive, high-risk refactoring of billing and scheduler code.

## Data Integrity & Edge Cases

When designing the Services 2 architecture, the following critical edge cases must be accommodated:
1. **Existing Services with Unmatched Categories:**
   Legacy services where `category = 'general'` or arbitrary strings not present in any formal category table.
2. **Packages with Zero Category:**
   All existing rows in `service_packages` have no category. They must default cleanly to a "General" or "Uncategorized" category during migration/transition.
3. **Deleting a Category Containing Active Services or Bundles:**
   Must prevent accidental deletion or reassign items to a default category to prevent orphaned catalog items.
4. **Deleting a Service Referenced by an Existing Bundle:**
   PostgreSQL FK constraint `service_package_items_service_id_fkey` blocks deletion. Must either prevent service deletion with a descriptive error ("Cannot delete service because it is part of Bundle X") or handle dissociation.
5. **Historical Appointments and Invoices:**
   Existing appointments have `packageSnapshot` and `packageId`. These historical snapshots must remain valid and intact regardless of future bundle or category schema changes.
6. **Bilingual Category Constraints:**
   Every category requires both Arabic (`name_ar`) and English (`name_en`) names to maintain full RTL/LTR fidelity across Tenant-v2 and mobile apps.

## Candidate Architecture Options

We evaluate **three distinct architecture options** based on the current codebase evidence:

### Option 1: Evolutionary Extended Model (Recommended)
*Extend `service_packages` with Category linkage + Hybrid Tenant Categories in `service_categories`.*

- **Database Changes:**
  1. Add `category` (`VARCHAR(255)`) or `categoryId` (`UUID NULL REFERENCES service_categories(id)`) to `service_packages`.
  2. Add `tenantId` (`UUID NULL REFERENCES tenants(id)`) to `service_categories`.
  3. Modify index on `service_categories`: Drop global unique on `slug`; add unique composite index on `(tenantId, slug)` where `tenantId IS NOT NULL` (and unique slug where `tenantId IS NULL`).
- **Backend Changes:**
  1. Add tenant CRUD routes for categories: `POST`, `PUT`, `DELETE` at `/api/v1/tenant/services/categories`.
  2. Update `tenantPackageController.js` to accept and persist category.
  3. Provide a unified catalog endpoint `GET /api/v1/tenant/catalog` (or extend `getServices` and `getPackages`).
- **Frontend Changes:**
  1. In `Services2Workspace.tsx`, implement category management (Add/Edit/Delete Category) alongside Services and Bundles.
  2. In `AppointmentServicesStep.tsx`, remove the top-level Services/Packages split; render Bundles beneath their category alongside Services.
- **Pros:**
  - **Zero disruption to existing booking engine:** `bookingService.js` continues processing `service_packages` and `service_package_items` without modification.
  - 100% backwards-compatible with existing appointment snapshots and invoicing.
  - Lowest migration risk.
- **Cons:**
  - Backend model remains named `ServicePackage` while UI displays "Bundle" (addressed via adapter aliasing).

---

### Option 2: Dedicated `tenant_categories` Table + Package Extension
*Isolate Tenant Categories in a new table, leaving Super Admin categories untouched.*

- **Database Changes:**
  1. Create new table `tenant_service_categories` (`id`, `tenantId`, `name_en`, `name_ar`, `slug`, `sortOrder`, `isActive`).
  2. Add `tenantCategoryId` to `services` and `service_packages`.
- **Backend Changes:**
  1. Build dedicated `tenantCategoryController.js`.
  2. Map both services and packages to `tenant_service_categories`.
- **Pros:**
  - Completely separates tenant data from Super Admin global taxonomy; zero risk of startup seeder collisions.
- **Cons:**
  - Requires maintaining two parallel category tables (`service_categories` for Super Admin / customer marketplace vs `tenant_service_categories` for tenant salons).
  - Customer app search must query and merge both category schemas.

---

### Option 3: Polymorphic Unified Catalog Table (`catalog_items`)
*Merge Services and Packages into a single polymorphic table.*

- **Database Changes:**
  1. Create `catalog_items` table with `itemType: 'SERVICE' | 'BUNDLE'`.
  2. Migrate all `services` and `service_packages` into `catalog_items`.
- **Backend Changes:**
  1. Complete rewrite of `bookingService.js`, `tenantServiceController.js`, `tenantPackageController.js`, `customer_invoices`, and scheduler queries.
- **Pros:**
  - Pure theoretical relational elegance.
- **Cons:**
  - **Extremely high migration risk.** Breaks historical appointment foreign keys, invoices, and requires rewriting thousands of lines of tested code.

# Phase 2 Gate

### 1. What We Definitively Know
- Categories are currently **100% Super Admin / Global**; tenants have **zero CRUD mutability** today.
- The link between `services` and `service_categories` is a **loose string literal**, not an enforced foreign key.
- Packages have **no category association whatsoever** today.
- The appointment drawer derives categories **client-side** from loaded services, causing Packages to be isolated into a separate tab.
- The backend booking engine (`bookingService.js:723-818`) already supports multi-service packages with variants, staff assignment, sequencing, and atomic appointment generation.

### 2. What We Definitively Do Not Know
- Whether product leadership desires subcategory nesting in Services 2.
- Whether bundles will be sold as prepaid multi-session vouchers/cards or strictly as same-day chained salon appointments.

### 3. Can the Database Support Services 2 Without Structural Changes?
**NO.** At minimum, adding a `category` (or `categoryId`) column to `service_packages` and enabling tenant ownership on categories requires a database migration. However, this can be achieved through **non-destructive, backwards-compatible schema extensions**.

### 4. Can Packages Safely Serve as Bundles at the Persistence Layer?
**YES.** `ServicePackage` and `ServicePackageItem` already model all core relational requirements of a Bundle. Adopting an adapter pattern where the UI presents "Bundles" while the persistence layer stores `ServicePackage` is safe, elegant, and avoids high-risk database refactoring.

### 5. Do Tenant-Owned Categories Require a New Table or Can Existing Tables Be Reused?
**Existing table `service_categories` can be safely reused** by adding a nullable `tenantId` column (`NULL` = global default, `UUID` = tenant custom) and updating the unique slug index to be composite (`UNIQUE (tenantId, slug)`). Alternatively, Option 2 (a dedicated `tenant_service_categories` table) can be used if complete physical isolation from Super Admin categories is preferred.

### 6. What Must Be Decided Before Phase 3?
- Choose between **Option 1** (Hybrid `service_categories` extension) and **Option 2** (Dedicated `tenant_service_categories` table).
- Decide bundle pricing rules (fixed price override vs percentage discount).

### 7. What MUST NOT Be Changed Yet?
- **DO NOT** modify `ServicesWorkspace.tsx`, `PackagesWorkspace.tsx`, or `Services2Workspace.tsx`.
- **DO NOT** modify `AppointmentServicesStep.tsx` or `InteractiveDrawers.tsx`.
- **DO NOT** create or execute any database migrations.
- **DO NOT** modify backend models or controllers.
- **DO NOT** commit or push any changes.
